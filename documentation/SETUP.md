# Set up PackPilot with the current services

This is a manual setup for a **new, empty installation**. Use your own Supabase Cloud, Cloudflare, Google OAuth and Brevo accounts. No hosting architecture change is required. The provider deployment steps have not yet been exercised end to end for this public candidate; test an independent staging instance before real use.

## 1. Create provider resources

- **Supabase:** create separate production and staging projects. Keep their project references, public URLs and browser publishable keys separate. Save privileged keys and database passwords in a secure store.
- **Cloudflare Pages:** choose separate production/staging project names and HTTPS origins. Use your own domain or Pages hostnames. Keep a private R2 Standard backup bucket; disable public bucket access.
- **Google Cloud:** create a web OAuth client. Register each Supabase callback, `https://PROJECT_REF.supabase.co/auth/v1/callback`. Keep the client secret in each Supabase Google provider setting. Configure permitted users/consent publication as appropriate.
- **Brevo:** verify your sender/domain and obtain a server-side API key. This version sends through the Brevo API; arbitrary SMTP credentials alone will not replace it. Configure Auth SMTP or its protected email hook separately if using Auth-generated mail.

Official guides: [Google sign-in](https://supabase.com/docs/guides/auth/social-login/auth-google), [Supabase OAuth server](https://supabase.com/docs/guides/auth/oauth-server), [Cloudflare Pages](https://developers.cloudflare.com/pages/), [Brevo sending setup](https://developers.brevo.com/docs/send-a-transactional-email), [R2 private buckets](https://developers.cloudflare.com/r2/).

## 2. Configure the source before its first migration

Follow [CONFIGURATION.md](CONFIGURATION.md): copy the example instance JSON into ignored .local/, enter non-secret settings, preview the changes, then apply them. Review the diff. The first administrator must use the verified Google email configured here.

Do this in a private instance checkout before deploying its first schema. Applied migrations become immutable afterward. Keep tokens/passwords out of this configuration and out of Git.

## 3. Install dependencies and verify locally

```bash
npm ci
npm run check
python -m pip install -r scripts/requirements.txt -r scripts/release/requirements.txt
python -m unittest discover -s tests -p 'test_*.py'
```

The catalog and inventory shipped here are synthetic test data. Review the policy templates in documentation/policies/ for your organization. The normal build generates matching policy hashes/pages and a temporary policy SQL seed.

## 4. Apply the database schema to staging first

Authenticate the Supabase CLI yourself, link the intended staging project and verify its project reference before applying migrations:

```bash
npx supabase login
npx supabase link --project-ref YOUR_STAGING_PROJECT_REF
npx supabase db push
```

For the initial empty installation, apply the policy seed generated by npm run generate:policies using that project's SQL editor or administrator connection. The default output is /tmp/pack99-policy-seed.sql. Never paste real roster records into logs or issues. Record the applied source revision and migration history.

Repeat against the new production project only after staging checks pass. These CLI instructions are not a migration/rollback procedure for an already populated installation.

## 5. Configure Auth and deploy the backend

Enable Google sign-in in Supabase Auth. Set its Site URL to the exact environment's website origin and allow the /oauth/consent callback. Enable Supabase's OAuth 2.1 server and configure Authorization Path /oauth/consent and compatible client registration. Google signs users in; Supabase separately authorizes MCP clients as those users.

In an ignored secrets file, set the matching AUTH_UI_ORIGIN, PACK99_ENVIRONMENT (staging or production), MCP_RESOURCE_URL and, if needed, APP_SUPABASE_PUBLISHABLE_KEY. For notifications, also set PACK99_AUTH_UI_ORIGIN to that environment’s exact website origin. Keep PACK99_DELIVERY_PAUSED=true. Notifications additionally use PACK99_DATABASE_KEY, BREVO_API_KEY, PACK99_FROM_EMAIL and PACK99_DISPATCH_SECRET. The database key is privileged and must remain server-only.

```bash
npx supabase secrets set --project-ref YOUR_PROJECT_REF --env-file .local/functions.env
npx supabase functions deploy scouts-mcp --project-ref YOUR_PROJECT_REF
npx supabase functions deploy parent-notifications --project-ref YOUR_PROJECT_REF
npx supabase functions deploy notification-links --project-ref YOUR_PROJECT_REF
```

Staging also needs the staging-auth-email function and protected Auth email hook if Auth mail is enabled. Configure its webhook signing secret and test-recipient protection through your provider settings; do not reuse production credentials or user sessions. Keep staging's PACK99_EMAIL_ALLOWLIST limited to the owned test inbox.

The retained deployment guards require the configured Supabase project and browser origins to match. Missing/mismatched configuration must stop deployment, not fall back to another project.

## 6. Build and publish the website

Supply the intended environment's VITE_SUPABASE_URL and VITE_SUPABASE_PUBLISHABLE_KEY through ignored local environment files or the build runner. Never use a service-role/secret key in the browser.

```bash
npm run build:auth -- --mode staging
npx wrangler login
npx wrangler pages project create YOUR_STAGING_PAGES_PROJECT --production-branch main
npx wrangler pages deploy auth-ui/dist --project-name YOUR_STAGING_PAGES_PROJECT --branch main
```

For the first production installation, build in production mode with its matching public configuration and use its own Pages project. Upload only auth-ui/dist. Keep HTTPS, the generated routing/security-header files and the policy pages. Check release.json against the source commit.

## 7. Verify access, import your own records and enable delivery deliberately

Sign in as the configured administrator. Review/accept policies, approve leader capabilities and establish parent/family links. Test an approved leader, an unapproved account, a restricted leader, and separate synthetic families. Verify denied cross-family access and unauthenticated MCP requests. Configure an OAuth-capable AI client with the environment's /functions/v1/scouts-mcp URL and complete real sign-in/consent testing.

The roster importer expects the [example non-health columns](../examples/README.md) and a worksheet named Roster 2026-27; rename/map your private source explicitly rather than silently guessing fields. Generate private SQL with scripts/import_roster.py, review its validation report and apply it only to the intended project. Supply a reviewed adventure catalog with appropriate permissions; bundled test definitions are not real advancement requirements.

Establish private backups, readback/freshness checks, an isolated restore rehearsal and independent recovery access before importing real family data. Read ReleaseRunbook.md. The deployment/backup workflow examples in documentation/workflow-examples/ are inactive and require your instance settings and review; the original live-instance adoption/acceptance records do not belong here.

Before enabling notification scheduling, verify the intended sender, recipients, links and outbox state using owned test identities. Keep delivery paused while doing setup. scripts/deploy-notification-scheduler.py supports an explicit --apply step after operator review; it enables the five-minute schedule. It is not a test message sender and must not be invoked with arbitrary live credentials. Never invoke an authenticated dispatcher merely to test deployment.
